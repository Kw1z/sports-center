# BluePulse — система записи в спортивный центр

**BluePulse** — учебное веб-приложение для просмотра услуг, тренеров и расписания спортивного центра, регистрации пользователей и бронирования занятий.

Проект состоит из трёх частей:

- **Frontend:** React, TypeScript, Vite, Material UI.
- **Backend:** Python, FastAPI, SQLAlchemy, JWT-авторизация.
- **База данных:** PostgreSQL 17 в Docker.

> Инструкция рассчитана на **Windows и PowerShell**. Команды выполняются из корня проекта, если не указано иное.

## 1. Что нужно установить

- Git и SourceTree (для работы с репозиторием).
- Docker Desktop (для PostgreSQL).
- Python 3.14.
- Node.js и npm (для Frontend).
- VS Code или другой редактор.

Исходный код: https://github.com/Kw1z/sports-center

## 3. Настройка PostgreSQL

Откройте **PowerShell в корневой папке проекта**.

Создайте корневой `.env` из примера:

```powershell
Copy-Item .env.example .env
```

Откройте `.env` и задайте собственный пароль. Пример структуры:

```dotenv
POSTGRES_USER=sport_app
POSTGRES_PASSWORD=ВАШ_СОБСТВЕННЫЙ_ПАРОЛЬ
POSTGRES_DB=sports_center
```

Пароль должен совпадать с `DB_PASSWORD` в `backend/.env`.

Запустите Docker Desktop, затем PostgreSQL:

```powershell
docker compose up -d db
```

Проверьте состояние:

```powershell
docker compose ps
```

Ожидаемый статус базы — `healthy`.

По умолчанию подключение к PostgreSQL:

| Параметр | Значение |
|---|---|
| Хост | `127.0.0.1` |
| Порт | `5432` |
| База | `sports_center` |
| Пользователь | `sport_app` |
| Пароль | Из корневого `.env` |

### Что создаётся автоматически

**Только при первом запуске с пустым хранилищем** Docker выполняет SQL-файлы из `compose.yaml`. В актуальной версии BluePulse они создают таблицы и начальный каталог:

- 6 услуг;
- 6 помещений;
- 6 тренеров;
- 60 будущих занятий (расписание относительно дня создания базы).

На существующем хранилище SQL-файлы автоматически повторно **не запускаются**. Не удаляйте тома PostgreSQL ради обновления данных: это может привести к потере пользователей и бронирований.

## 4. Настройка Backend

Откройте **второй терминал PowerShell** в корне проекта:

```powershell
cd backend
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Если `backend/.env` уже существует и настроен, **не перезаписывайте его** — пропустите команду `Copy-Item`.

Откройте `backend/.env` и укажите свои значения:

```dotenv
DB_HOST=127.0.0.1
DB_PORT=5432
DB_NAME=sports_center
DB_USER=sport_app
DB_PASSWORD=ВАШ_СОБСТВЕННЫЙ_ПАРОЛЬ
JWT_SECRET_KEY=ВАШ_СЛУЧАЙНЫЙ_СЕКРЕТ_НЕ_КОРОЧЕ_64_СИМВОЛОВ

DEMO_CLIENT_PASSWORD=ВАШ_ТЕСТОВЫЙ_ПАРОЛЬ_КЛИЕНТОВ
DEMO_ADMIN_PASSWORD=ВАШ_ТЕСТОВЫЙ_ПАРОЛЬ_АДМИНИСТРАТОРА
DEMO_STAFF_PASSWORD=ВАШ_ТЕСТОВЫЙ_ПАРОЛЬ_СОТРУДНИКОВ
```

- `DB_PASSWORD` должен **точно совпадать** с `POSTGRES_PASSWORD` из корневого `.env`.
- `JWT_SECRET_KEY` должен содержать случайную секретную строку длиной не менее 64 символов.
- Каждому `DEMO_*_PASSWORD` задайте пароль длиной не менее 12 символов. Используйте их **только локально для разработки**.
- Не публикуйте содержимое `.env` и реальные пароли.

Для генерации случайного секрета можно выполнить в PowerShell:

```powershell
.\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(64))"
```

Скопируйте результат в `JWT_SECRET_KEY`.

### Запуск API

Находясь в папке `backend`, выполните:

```powershell
.\.venv\Scripts\python.exe -m uvicorn main:app --reload
```

Адреса:

- API: http://127.0.0.1:8000
- Swagger UI: http://127.0.0.1:8000/docs

Терминал с Backend оставьте открытым.

## 5. Заполнение демонстрационной базы

**Предварительные условия:** PostgreSQL запущена и здорова (`healthy`), `backend/.env` настроен, Python-зависимости установлены. Для новой базы Docker уже создал таблицы, услуги, помещения, тренеров и занятия.

Откройте терминал в папке `backend` и выполните:

```powershell
.\.venv\Scripts\python.exe seed_demo_all.py
```

Скрипт покажет адрес подключения, скрыв пароль. **Проверьте хост, порт и имя базы**. Только если это нужная база, введите `YES` и нажмите Enter.

Скрипт последовательно запускает:

1. `seed_demo_clients.py` — создание 20 демонстрационных клиентов из `database/demo_clients.csv`.
2. `seed_demo_accounts.py` — создание администратора и 6 аккаунтов сотрудников с привязкой к тренерам.
3. `seed_demo_bookings.py` — создание до 120 бронирований для демоклиентов.

## 6. Запуск Frontend

Откройте **третий терминал PowerShell** в корне проекта:

```powershell
cd frontend
npm install
npm run dev
```

Откройте адрес, показанный Vite. Обычно это:

http://127.0.0.1:5173

Frontend использует прокси Vite: запросы `/api/...` отправляются на `http://127.0.0.1:8000`. Поэтому для работы функций, использующих API, FastAPI должен быть запущен.

> **Статус интеграции:** некоторые страницы Frontend могут пока использовать тестовые данные, пока они не подключены к соответствующим Backend-эндпоинтам. Например, наличие `GET /api/trainers` не гарантирует, что страница тренеров уже читает его.


Затем откройте сайт (обычно http://127.0.0.1:5173) и Swagger (http://127.0.0.1:8000/docs).

## 8. Безопасная проверка на отдельной базе

Чтобы протестировать **полностью новую** PostgreSQL, не затрагивая основную, используйте отдельный проект Docker Compose и другой порт. В **новом PowerShell из корня проекта**:

```powershell
$env:POSTGRES_HOST_PORT = "55433"
docker compose -p bluepulse_verify up -d db
```

После получения `healthy` откройте терминал Backend и задайте тестовый порт **до запуска Python**:

```powershell
cd backend
$env:DB_PORT = "55433"
.\.venv\Scripts\python.exe -c "from database import engine; print(engine.url.render_as_string(hide_password=True))"
```

Убедитесь, что в адресе указан `:55433/`, и только после этого запускайте `seed_demo_all.py`.

Переменные `$env:POSTGRES_HOST_PORT` и `$env:DB_PORT` действуют только в текущих терминалах PowerShell. В новых терминалах стандартное подключение будет определяться значениями из `.env`.

**Не выполняйте `docker compose down -v` без понимания последствий:** параметр `-v` удаляет тома с данными. Основную базу разработки удалять нельзя.

## 9. API и возможности

Backend реализует:

- Регистрацию, вход и получение текущего пользователя (`/api/auth/...`).
- Просмотр услуг (`/api/services`).
- Просмотр расписания (`/api/sessions`).
- Просмотр профилей тренеров (`/api/trainers`).
- Создание, просмотр и отмену собственных бронирований (`/api/bookings/...`).
- Административные операции управления каталогом, расписанием, пользователями и бронированиями.
- Просмотр занятий сотрудником.

Актуальный список методов, форматы запросов и права доступа смотрите в Swagger: http://127.0.0.1:8000/docs.

## 10. Частые проблемы

**Docker не запускает базу.** Убедитесь, что открыт Docker Desktop, затем выполните `docker compose ps`. Если порт `5432` занят, проверьте, не запущен ли другой PostgreSQL.

**Ошибка подключения к PostgreSQL из Backend.** Сравните `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER` и `DB_PASSWORD` в `backend/.env` с корневым `.env` и портом Docker.

**В базе старые данные.** Скрипты из `docker-entrypoint-initdb.d` работают только для пустого хранилища при первом создании. Не удаляйте существующую базу. Для безопасной проверки используйте отдельный проект из раздела 8.

**Пустая страница или ошибки запросов на сайте.** Проверьте, запущены ли одновременно PostgreSQL, FastAPI и Vite. Откройте Swagger и консоль разработчика браузера.

**Команда `py -3.14` не работает.** Проверьте установку Python 3.14 и доступность Python Launcher. При необходимости укажите установленную версию Python, совместимую с зависимостями проекта.

## 11. Совместная работа и безопасность

- Разработка ведётся в Git и SourceTree; изменения объединяются через ветки и pull request.
- Backend, Frontend и база запускаются **локально на каждом компьютере**.
- Начальные справочники и демоданные можно воспроизвести одинаковыми скриптами, но **локальные базы PostgreSQL не синхронизируются автоматически**: изменения бронирований на одном компьютере не появляются на другом.
- Занятия создаются относительно даты первоначального заполнения, поэтому календарные даты на двух устройствах могут отличаться.
- Не коммитьте файлы `.env`, пароли, токены, локальные базы данных или виртуальное окружение `.venv`.
- Демонстрационные пароли и пользователи предназначены только для локальной разработки, не для публичного сервера.
